# ADR-007: Політика доступу — JWT RS256, роль і володіння, перевірка у власнику даних

- **Статус:** Прийнято
- **Дата:** 2026-11-25
- **Пов'язані:** ADR-001 (ролі з ЛР 1), ADR-004 (REST API), ADR-006 / ADR-008 (шлюз)

## Контекст

До ЛР 8 Booking API приймав будь-який запит. Хто завгодно міг скасувати заняття або записати іншу людину. У ЛР 1 визначено три ролі: адміністратор, тренер і клієнт. Проте самої ролі мало: два тренери мають однакову роль, а скасовувати кожен має право лише своє заняття. Отже, рішення залежить ще й від того, **кому належить об'єкт**.

Обмеження:
- справжнього сервера OAuth 2.0 / OIDC на стенді немає, лише навчальний емітент;
- облікові дані й ключі мають бути синтетичними й лишатися поза Git;
- до Booking API можна звернутися напряму, без шлюзу (ЛР 7).

## Розглянуті варіанти

**Де перевіряти права**

| Варіант | Плюси | Мінуси |
|---|---|---|
| 1. Лише в шлюзі | одне місце для всіх сервісів | обхід шлюзу дає повний доступ; шлюз не знає, кому належить заняття, тому перевірити володіння не може |
| 2. Шлюз перевіряє токен, API — права | раннє відсікання сміття | дві копії конфігурації ключів і аудиторії; API однаково мусить перевіряти токен, бо не довіряє мережі |
| 3. **Токен і права перевіряє Booking API як власник даних**, шлюз лише передає `Authorization` | права перевіряються там, де є дані про власника; обхід шлюзу нічого не дає | кожен сервіс з даними мусить мати свою перевірку |

**Як підписувати токен**

| Варіант | Плюси | Мінуси |
|---|---|---|
| HS256 (спільний секрет) | простіше | кожен, хто перевіряє токен, може його й випустити; секрет треба роздати всім сервісам |
| **RS256** (пара ключів) | API має лише відкритий ключ і випустити токен не може | треба генерувати й зберігати пару ключів |

**Модель прав**

| Варіант | Мінуси |
|---|---|
| Лише роль (RBAC) | тренер Тарас міг би скасувати заняття тренерки Олени |
| **Роль + володіння об'єктом** | правила треба писати для кожної операції |

## Рішення

1. **Access token — JWT, підписаний RS256.** Перевірка бібліотекою PyJWT: дозволено лише `RS256`, обов'язкові `iss`, `aud`, `sub`, `iat`, `exp`; `iss = fitshed-local-issuer`, `aud = fitshed-booking-api`, допуск годинника 10 с. Роль у claim `role` має бути з відомого набору.
2. **Ідентичність лише з перевіреного токена.** `client_id` і `trainer_id` з тіла запиту лише порівнюються з `sub`.
3. **Перевіряє Booking API** (варіант 3): спершу автентифікація, далі авторизація в `api/authz.py`, лише потім доменне ядро. Шлюз передає заголовок без змін і не журналює його.
4. **Права = роль + володіння** (матриця в `docs/lab8/README.md`):
   - тренер створює й скасовує лише заняття з `trainer_id = sub`;
   - клієнт записує лише себе;
   - адміністратор може все.

   Під час читання клієнт бачить у списках лише себе, а тренер бачить повні списки лише свого заняття.
5. **401** означає, що автентифікації немає або вона невалідна (з `WWW-Authenticate: Bearer`). **403** означає, що автентифікацію пройдено, а права немає. Для чужого заняття відповідь 403, а не 404, бо розклад публічний і приховувати існування заняття нема чого. Перевірка 401 виконується раніше за перевірку тіла запиту (400).
6. **Ключі навчальні:** генеруються локально (`python -m fitshed.auth.keys`) у `backend/var/keys/`, шлях задається змінними оточення. Закритий ключ має лише емітент, API — лише відкритий. Строк дії токена — 15 хвилин.

## Зіставлення з першим модулем

- **Ролі** з ЛР 1 (діаграма контексту C4) збережено без змін. Нове лише правило володіння, якого ЛР 1 не вимагала.
- **ADR-001** (модульний моноліт): авторизація — окремий модуль на рівні адаптера HTTP. Доменне ядро `GroupClass` (ЛР 2) про ролі не знає, тож межі модулів не порушено.
- **ADR-003** (одна VM): емітент і API на одній машині. Для відкритого доступу з інтернету тепер обов'язковий TLS. Цей пункт додається до умов переходу ADR-003.

## Наслідки

**Позитивні:**
- обхід шлюзу не дає доступу;
- підроблений, прострочений або чужий токен відхиляється, і це перевірено тестами;
- тренер не може зіпсувати чуже заняття, клієнт — чужий запис;
- компрометація API не дає змоги випускати токени.

**Негативні:**
- немає відкликання токена до закінчення `exp` (до 15 хв);
- немає ротації ключів (`kid`, JWKS);
- сервіс абонементів (заглушка) не перевіряє токенів — ризик R5;
- правило володіння треба дописувати для кожної нової операції.

## Умова перегляду

- Замінити навчального емітента на справжній OIDC-провайдер (Keycloak, Auth0), коли з'являться реальні користувачі. Відкритий ключ тоді брати з JWKS за `kid`.
- Додати ротацію ключів, якщо строк життя системи перевищить рік або закритий ключ могли скомпрометувати.
- Додати автентифікацію між сервісами (mTLS або токени для сервісу), якщо сервіс абонементів стане доступний не лише з loopback.
- Перейти на політики як дані (наприклад, OPA), якщо кількість ролей або операцій зросте настільки, що матриця в коді стане складною для перевірки.
