# ADR-006: API Gateway з повторами, circuit breaker і rate limiting

- **Статус:** Прийнято
- **Дата:** 2026-11-25

## Контекст

Клієнти FitShed (веб-застосунок, згодом мобільний) звертаються до Booking API (ЛР 5) і до сервісу абонементів. Сервіс абонементів може відповідати повільно, тимчасово повертати 503 або бути недоступним повністю. Без захисту:
- зависла залежність тримає запит клієнта стільки, скільки вона зависла (у серії «до захисту» — до 2,1 с);
- кожна тимчасова 503 одразу стає помилкою для клієнта (8 з 30 у серії «до захисту»);
- під час повної відмови кожен запит клієнта однаково йде в залежність, не даючи їй відновитися (30 викликів із 30);
- один клієнт може надіслати стільки запитів, що заблокує решту.

Водночас бізнес-правила мають лишатися в Booking API та доменному ядрі (ADR-001, ADR-004), а не переходити в шлюз.

## Розглянуті варіанти

| Варіант | Плюси | Мінуси |
|---|---|---|
| 1. Політики в кожному сервісі окремо | немає додаткового компонента | ті самі таймаути, ліміти й breaker дублюються в кожному сервісі; немає єдиної точки для `request_id` і обмеження клієнтів |
| 2. Готовий шлюз (Envoy, Kong, nginx) | промислові реалізації retry, breaker, rate limiting; висока продуктивність | окрема конфігураційна мова, складніше відтворювати й перевіряти збої в автоматичних тестах на локальному стенді |
| 3. Власний легкий шлюз на Starlette з перевіреними політиками | кожна політика видима в коді й перевірена тестами з керованим часом; той самий стек, що й Booking API | власну реалізацію треба підтримувати; поступається готовим шлюзам за продуктивністю й можливостями |

## Рішення

Обрано **варіант 3** для навчального стенда: шлюз на Starlette з такими політиками (`backend/config/gateway.json`):

| Політика | Значення |
|---|---|
| Таймаут спроби (читання) | 0,5 с |
| Загальний deadline (читання) | 2,0 с |
| Спроби (читання) | до 3, exponential backoff 0,1–1,0 с з full jitter |
| Повтор дозволено | лише `GET` і лише для таймауту, обриву з'єднання, 502, 503, 504 |
| Операції зміни стану | одна спроба, таймаут 2,0 с, без повторів |
| Circuit breaker | на кожну залежність; відкриття після 5 відмов поспіль, 3 с у стані open, 1 проба в half-open |
| Rate limiting | token bucket за `X-Api-Key`, 20 запитів пачкою, 10/с, відповідь 429 з `Retry-After` |

У промисловій системі ті самі значення варто перенести в готовий шлюз (варіант 2), а власний код залишити як перевірену специфікацію поведінки.

## Компроміс: швидка відмова, навантаження й шанс відновлення

Виміряно на стенді (`docs/lab7/comparison.md`, по 30 запитів):

| | Нестабільна залежність | Повна недоступність |
|---|---|---|
| Успіхів до / після | 22 / 30 | 0 / 0 |
| Викликів залежності до / після | 30 / **56** | 30 / **5** |
| Максимальний час до / після, мс | 2080 / 805 | 45 / 271 |

- **Повтори підвищують шанс успіху, але збільшують навантаження.** За нестабільної залежності вони врятували всі 8 запитів, проте залежність отримала майже вдвічі більше викликів. Якщо вона збоїть саме через перевантаження, повтори його посилять. Тому спроб лише 3, з паузами й jitter, а deadline обмежує сумарний час.
- **Breaker дає швидку відмову й знижує навантаження, але відкладає відновлення.** За повної відмови він скоротив виклики з 30 до 5, а відповідь в open займає 4–5 мс. Ціна: протягом 3 с після відновлення залежності клієнти ще отримують 503, доки проба не закриє breaker.
- **Значення параметрів визначають, що саме ми обираємо:**
  - нижчий поріг breaker (наприклад, 3 відмови) — швидше захищає залежність, але частіше відкривається через випадкові збої;
  - довший `open_timeout` — більше часу залежності на відновлення, але довша недоступність для клієнтів;
  - більше спроб або довший deadline — вищий шанс успіху, але довше чекання клієнта й більше навантаження.
  
  Для FitShed обрано помірні значення. Читання абонемента не критичне за часом, але й чекати понад 2 с клієнт не повинен.

## Наслідки

**Позитивні:**
- клієнт чекає не довше deadline навіть за зависання залежності;
- тимчасові збої читань непомітні для клієнта;
- під час відмови залежність не отримує потоку запитів;
- один клієнт не може витратити ресурси, призначені іншим;
- `request_id` дозволяє простежити запит від шлюзу до залежності.

**Негативні:**
- ще один компонент і ще одна точка відмови на шляху кожного запиту;
- стан breaker і rate limiting у пам'яті одного процесу: кілька копій шлюзу не узгоджують лічильники;
- операції зміни стану за таймауту повертають 504, і клієнт не знає, чи відбулася дія;
- повтори збільшують навантаження на залежність.

## Умова перегляду

- Перейти на готовий шлюз (Envoy, Kong), якщо шлюз потрібно запускати в кількох копіях або потрібні можливості, яких немає у власній реалізації (TLS, автентифікація, метрики).
- Винести стан rate limiting у спільне сховище (наприклад, Redis), якщо копій шлюзу стане кілька.
- Дозволити повтори для операцій зміни стану лише після узгодження ключа ідемпотентності (заголовок `Idempotency-Key`, як `event_id` у ЛР 6) у Booking API і сервісі абонементів.
- Переглянути значення порогів, якщо вимірювання на реальному навантаженні покажуть, що breaker відкривається через поодинокі збої або повтори помітно навантажують залежність.
