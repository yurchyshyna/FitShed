# ADR-001: Модульний моноліт з окремим фоновим воркером

- **Статус:** Прийнято
- **Дата:** 2026-11-23

## Контекст

FitShed розробляє одна людина. Система обслуговує один клуб: близько 600 клієнтів, 12 тренерів, до 100 одночасних користувачів у вечірній пік.

Від архітектури вимагається:
- одночасний запис на останні місця не повинен давати перевищення місткості, а абонемент має списуватися рівно один раз (СЯ-1);
- сповіщення про зміну розкладу мають доходити за 5 хвилин навіть за тимчасових збоїв сервісу повідомлень, причому дія адміністратора не повинна чекати на розсилку (СЯ-2);
- перегляд розкладу і запис у пік мають p95 ≤ 500 мс (СЯ-3).

Дані тісно пов'язані: заняття, запис, абонемент і лист очікування змінюються разом.

## Розглянуті варіанти

1. **Мікросервіси:** окремі сервіси розкладу, запису, абонементів, сповіщень і звітів, кожен зі своєю базою, взаємодія через HTTP та брокер повідомлень.
2. **Простий моноліт:** один процес, який і відповідає на запити, і надсилає сповіщення та рахує звіти під час запиту.
3. **Модульний моноліт з окремим воркером:** одна кодова база з чіткими модулями, яка запускається як два процеси: Backend API і фоновий воркер, з однією базою PostgreSQL.

## Рішення

Обрано **варіант 3**.

Код поділено на модулі: `schedule`, `booking` (запис і лист очікування), `memberships`, `attendance`, `notifications`, `reports`. Модулі звертаються один до одного лише через публічні функції, а не напряму до чужих таблиць.

Запис на заняття виконується в одній транзакції з блокуванням рядка заняття. Фонові завдання API записує в таблицю черги в тій самій транзакції, що й зміну даних, а воркер їх забирає. Так подія не губиться, навіть якщо воркер на якийсь час зупиниться.

Варіант 2 відкинуто, бо розсилка 30 сповіщень і повтори при збоях блокували б відповідь адміністратору, а нічні звіти навантажували б API в робочий час. Варіант 1 відкинуто, бо запис довелося б розносити між сервісами абонементів і запису з розподіленою транзакцією, а для одного розробника це лише випадкова складність.

## Наслідки

**Позитивні:**
- узгодженість запису гарантує транзакція бази даних, без складних механізмів (СЯ-1);
- розсилка й звіти не впливають на час відповіді API (СЯ-2, СЯ-3);
- одне розгортання, один набір тестів, проста локальна розробка;
- API і воркер можна масштабувати окремо.

**Негативні:**
- модулі не можна випускати незалежно: будь-яка зміна означає новий реліз усієї системи;
- межі між модулями тримаються на дисципліні, тому їх варто перевіряти в CI (наприклад, інструментом `import-linter`);
- одна база є спільною точкою відмови, тому потрібні резервні копії та перевірка відновлення;
- черга в PostgreSQL розрахована на помірну кількість завдань.

## Умова перегляду

Рішення переглядається, якщо виконується хоча б одна умова:
- система обслуговує мережу з понад 10 клубів або понад 20 000 клієнтів, і p95 запису перевищує 500 мс навіть після масштабування API;
- кількість сповіщень зростає настільки, що черга в PostgreSQL не встигає доставляти їх за 5 хвилин при кількох воркерах;
- над проєктом працює понад одну команду (5–6 розробників), і спільні релізи починають гальмувати роботу.

Першим кандидатом на виділення є модуль `notifications`, бо він уже спілкується з рештою системи лише через чергу завдань і не бере участі в транзакції запису.
