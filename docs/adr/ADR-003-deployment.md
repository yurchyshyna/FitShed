# ADR-003: Розміщення FitShed на одній VM з Docker Compose на поточному етапі

- **Статус:** Прийнято
- **Дата:** 2026-11-24

## Контекст

Логічна архітектура FitShed визначена в ADR-001: чотири контейнери C4 (веб-застосунок, Backend API, фоновий воркер, PostgreSQL). Потрібно вирішити, де і як їх розміщувати.

Аналіз ризиків у ЛР 4 показав, що СЯ-1 (одночасний запис) і СЯ-2 (сповіщення за 5 хвилин без втрат) залежать насамперед від бази даних: від її доступності, швидкості відновлення та запасу ресурсів.

Поточний етап: один клуб, близько 100 одночасних користувачів у пік, один розробник, обмежений бюджет.

## Розглянуті варіанти

| | Варіант | J за W1 (поточний етап) | J за W2 (мережа клубів) |
|---|---|---|---|
| A | Одна VM, Docker Compose | **0,250** | 0,700 |
| B | VM + керована PostgreSQL | 0,311 | 0,425 |
| C | Керований Kubernetes + керована PostgreSQL | 0,750 | **0,300** |

Критерії: витрати, час відновлення (RTO), складність супроводу, запас масштабування. Значення синтетичні, розрахунок: `evaluation/mcda.py`, звіт: `docs/lab4/results.md`.

## Рішення

Обрано **варіант A** для поточного етапу з обов'язковими заходами:
- дані PostgreSQL зберігаються в окремому Docker volume;
- щоденна резервна копія бази в окреме сховище поза VM;
- відновлення з копії перевіряється щонайменше раз на місяць, а час відновлення фіксується як фактичний RTO;
- для всіх контейнерів задано healthcheck і політику автоматичного перезапуску.

## Наслідки

**Позитивні:**
- найменші витрати й найпростіший супровід: той самий Docker Compose, що й для локальної розробки;
- одне середовище для всієї системи, просте налагодження.

**Негативні:**
- VM — єдина точка відмови: при її падінні недоступні і API, і воркер, і черга сповіщень, тож СЯ-2 у цей час не виконується;
- RTO близько години (за припущенням) і можлива втрата даних з моменту останньої копії;
- запас масштабування обмежений однією машиною.

## Обмеження

- Усі показники порівняння синтетичні: витрати не є тарифами провайдера, RTO і запас не виміряні.
- Аналіз чутливості показав, що вибір нестійкий: якщо перенести 0,10 ваги з витрат на RTO, перемагає варіант B.
- Оцінки J мають сенс лише для множини {A, B, C}. Без варіанта C за ваг W2 перемагає B.

## Умови перегляду

Рішення переглядається, якщо виконується хоча б одна умова:
- **Перехід на B:** клуб починає реально працювати з системою, і простій понад 15–20 хвилин або втрата записів за день стають неприйнятними; або перевірка відновлення показує фактичний RTO понад 60 хвилин; або навантажувальний тест СЯ-3 показує, що база й API конкурують за ресурси VM і p95 перевищує 500 мс.
- **Перехід на C:** FitShed обслуговує мережу клубів (пріоритети W2), понад 300 одночасних користувачів, або потрібні оновлення без простою.
- Виміряні значення витрат, RTO чи запасу суттєво відрізняються від синтетичних, і повторний розрахунок за тими самими формулами дає інший вибір.

Варіант B розглядається як наступний крок, бо логічна архітектура при переході не змінюється: потрібно лише винести базу з Docker Compose у керований сервіс і змінити рядок підключення.
