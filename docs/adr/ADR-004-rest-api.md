# ADR-004: REST API для контексту «Розклад і запис»

- **Статус:** Прийнято
- **Дата:** 2026-11-24

## Контекст

До доменного ядра «Розкладу і запису» (ЛР 2) потрібно додати API. Його використовуватимуть:
- веб-застосунок на React, який працює в браузері клієнта, тренера й адміністратора (ЛР 1);
- надалі інші модулі чи сервіси, наприклад «Абонементи», якщо їх буде винесено окремо (умова перегляду ADR-001).

Для порівняння взято дві вимоги FitShed:
1. **Доступ із браузера** без додаткових посередників і з простим налагодженням (адаптивний веб-застосунок, ЛР 1).
2. **Явні переходи стану й зрозумілі помилки**: клієнт має відрізняти «некоректні дані», «немає заняття» і «заняття вже скасоване» (інваріанти й стани з ЛР 2).

## Розглянуті варіанти

| Критерій | REST (HTTP + JSON) | gRPC | GraphQL |
|---|---|---|---|
| **Вимога 1: браузер** | працює напряму через `fetch`, відповіді видно в DevTools, легко перевірити `curl` | браузер не підтримує gRPC напряму, потрібен gRPC-Web і проксі | працює з браузера, але потрібні бібліотека клієнта й сервер GraphQL |
| **Вимога 2: переходи й помилки** | ресурс і дії лягають на методи (`POST /cancellation`), помилки — на коди 400/404/409, які розуміє будь-який HTTP-інструмент | є власні коди статусу, контракт суворо типізований у `.proto` | зазвичай завжди 200, помилки передаються в полі `errors`, клієнту треба розбирати їх самостійно |
| Контракт | OpenAPI 3.1 | `.proto`, генерація коду | схема GraphQL |
| Сильна сторона | простота, кешування `GET`, інструменти | швидкий двійковий обмін між сервісами, потоки | клієнт сам обирає поля, менше запитів для складних екранів |
| Для FitShed зараз | один клієнт, кілька простих ресурсів | немає міжсервісних викликів (модульний моноліт) | екрани прості, вибір полів не дає відчутної вигоди |

## Рішення

Обрано **REST** з контрактом в **OpenAPI 3.1.1** (`backend/openapi.yaml`). Реалізація — **FastAPI** (як у контейнері Backend API з ADR-001) з сервером uvicorn.

- Ресурс — групове заняття `/classes`; дії над станом виражено як підресурси (`/bookings`, `/cancellation`), а не як редагування поля `status`.
- Помилки — `application/problem+json` (RFC 9457) з кодами 400, 404, 409.
- Помилки валідації FastAPI (за замовчуванням 422) перекладаються в 400 у тому самому форматі, щоб клієнт мав один спосіб обробки помилок.
- Сумісність клієнта й провайдера перевіряється контрактними тестами за файлом очікувань (`backend/contracts/`).

gRPC і GraphQL не реалізуються.

## Наслідки

**Позитивні:**
- веб-застосунок звертається до API напряму з браузера;
- кожен тип помилки має свій HTTP-код, тож клієнт обробляє їх без розбору тексту;
- контракт лежить поруч із кодом, а несумісні зміни ловлять контрактні тести.

**Негативні:**
- для складних екранів (наприклад, «розклад тижня з тренерами й залишком абонемента») може знадобитися кілька запитів або окремий ендпоінт під екран;
- текстовий JSON повільніший за двійковий gRPC, якщо колись з'являться інтенсивні виклики між сервісами;
- сумісність версій контракту треба стежити вручну (контрактні тести, правила додавання лише необов'язкових полів).

## Умова перегляду

- **gRPC** — для внутрішніх викликів, якщо модулі «Абонементи» чи «Сповіщення» буде винесено в окремі сервіси (умова перегляду ADR-001) і між ними з'явиться інтенсивний обмін. Зовнішнє API для браузера при цьому лишиться REST.
- **GraphQL** — якщо з'явиться кілька різних клієнтів (наприклад, мобільний застосунок і панель мережі клубів), яким потрібні різні набори полів, і кількість спеціальних REST-ендпоінтів під екрани почне швидко зростати.
