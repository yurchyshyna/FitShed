# Лабораторна робота №5 (модуль 2, ЛР 1). Проєктування API та перевірка контрактів

Система: **FitShed**. До доменного ядра контексту «Розклад і запис» з ЛР 2 додано HTTP API, клієнта, що працює через нього, і контрактні перевірки між ними.

## 1. Ресурс, власник даних і переходи стану

**Ресурс** — групове заняття (`/classes`).

**Власник даних** — модуль `booking` (контекст «Розклад і запис»). Лише він зберігає заняття, записи й лист очікування. Інші компоненти (веб-застосунок, воркер, модуль «Абонементи») змінюють заняття тільки через цей контракт. Прямого доступу до сховища заняття в них немає: щоб записати клієнта, треба викликати `POST /classes/{id}/bookings`, а не дописати рядок у таблицю.

**Операції:**

| Операція | Метод і шлях | Що робить |
|---|---|---|
| Створення | `POST /classes` | створює заняття зі статусом `scheduled` |
| Читання | `GET /classes/{class_id}` | повертає заняття з поточним станом, записаними й листом очікування |
| Зміна стану записів | `POST /classes/{class_id}/bookings` | записує клієнта або ставить у лист очікування |
| Перехід стану | `POST /classes/{class_id}/cancellation` | переводить заняття `scheduled → cancelled` |

**Дозволені переходи** (з ЛР 2, не змінювалися): `scheduled → cancelled`, `scheduled → completed`; зі `cancelled` і `completed` переходів немає. Записи змінюються лише в стані `scheduled` до початку заняття. Ці правила перевіряє доменне ядро, а API лише перекладає порушення в код 409.

## 2. Контракт: OpenAPI

Специфікація: [`backend/openapi.yaml`](../../backend/openapi.yaml), версія **OpenAPI 3.1.1**. Вона лежить поруч із кодом і містить обов'язкові поля, типи, обмеження (`minLength`, `minimum`/`maximum`, `enum`, `additionalProperties: false`), приклади, успішні відповіді та помилки.

### Вибір методу й статус-коду

| Операція | Метод | Код успіху | Чому так |
|---|---|---|---|
| Створити заняття | `POST` | **201 Created** + `Location` | ідентифікатор призначає сервер, тому `POST` на колекцію, а не `PUT`. Заняття створено одразу й повністю, тож 201, а адреса нового ресурсу в `Location` |
| Отримати заняття | `GET` | **200 OK** | безпечне читання, нічого не змінює, можна повторювати |
| Записати клієнта | `POST` | **201 Created** | кожен виклик створює новий запис, тому не ідемпотентний `POST`. Запис зроблено синхронно ще до відповіді (місце або лист очікування), тож 201, а не 202 |
| Скасувати заняття | `POST` на підресурс `/cancellation` | **200 OK** | це бізнес-дія, а не редагування поля. `PATCH status` дозволив би клієнту записати довільний стан, а так дозволено лише одну дію, і допустимість переходу перевіряє домен. Стан змінено синхронно, у відповіді оновлене заняття |

### Помилки

Усі помилки повертаються у форматі `application/problem+json` (RFC 9457) з полями `status`, `code`, `title`, `detail`. `detail` пояснює причину людською мовою.

| Код | `code` | Коли |
|---|---|---|
| 400 | `invalid_input` | не JSON, немає обов'язкового поля, неправильний тип, зайве поле, неприпустимі значення (кінець раніше початку, понад 40 місць) |
| 404 | `not_found` | заняття з таким `class_id` немає |
| 405 | `invalid_input` | метод не підтримується для цього шляху (заголовок `Allow`) |
| 409 | `invalid_state` | заборонений перехід: запис на скасоване чи розпочате заняття, повторне скасування |
| 409 | `rule_violation` | порушено бізнес-правило: клієнт уже записаний |

### 201 чи 202

**201** означає, що ресурс уже створено до відповіді. **202** — що запит лише прийнято до обробки, а результат буде пізніше й не гарантований.

У FitShed запис на заняття й скасування виконуються синхронно в доменному ядрі, тому 201 і 200. А от **сповіщення** записаним клієнтам після скасування надсилає воркер пізніше (ЛР 1, СЯ-2), і відповідь 200 цього не гарантує. Якби запис з оплатою абонементом ішов через Saga з ЛР 3 у фоновому воркері, тоді `POST /bookings` мав би повертати **202** з посиланням на стан процесу, бо в момент відповіді ще невідомо, чи вдасться списати відвідування.

## 3. Вибір стилю API

Порівняння REST, gRPC і GraphQL за двома вимогами FitShed і рішення зафіксовано в [ADR-004](../adr/ADR-004-rest-api.md). Коротко: обрано REST, бо основний клієнт — браузер (React-застосунок з ЛР 1), а ресурси й переходи стану природно лягають на HTTP-методи та коди.

## 4. Реалізація

```
backend/
├── openapi.yaml                       # контракт
├── contracts/
│   └── booking-client.expectations.json   # файл очікувань клієнта
└── src/fitshed/api/
    ├── http_api.py    # HTTP-адаптер доменного ядра (транспорт → BookingService)
    ├── server.py      # локальний сервер на http.server
    ├── client.py      # клієнт API (споживач контракту)
    └── scenario.py    # завершений сценарій через API
```

**API як адаптер.** `http_api.py` лише розбирає шлях і JSON, перевіряє структуру й типи та перекладає доменні помилки в коди HTTP. Далі він викликає `BookingService` з ЛР 2, а той працює з агрегатом `GroupClass` через порт сховища. Доменне ядро не змінилося. До прикладного сервісу додано лише метод читання `get_class`, щоб API не звертався до сховища напряму.

**Які правила де перевіряються:**

| Рівень | Що перевіряє |
|---|---|
| HTTP-адаптер | чи це JSON, чи є всі поля, чи правильні типи, чи немає зайвих полів, чи дата у форматі ISO 8601 |
| Доменне ядро (без змін з ЛР 2) | кінець пізніше за початок, тривалість до 3 год, місць від 1 до 40, не більше записаних, ніж місць, без повторного запису, дозволені переходи, записи лише до початку |

**Чому без FastAPI.** У ADR-001 для Backend API заплановано FastAPI. Для цієї роботи адаптер написано на стандартній бібліотеці Python (`http.server`, `urllib`), щоб локальний запуск не потребував додаткових пакетів, а транспорт був видно повністю. Оскільки це лише адаптер, його можна замінити на FastAPI, не змінюючи ні доменного ядра, ні контракту: тести API й контрактні перевірки працюють через HTTP і перевіряли б нову реалізацію так само.

**Сховище.** Адаптер у пам'яті з ЛР 2. Сервер однопотоковий (`HTTPServer`): запити обробляються по черзі, тож конкурентного запису в межах цього прототипу не буває. Після зупинки сервера дані зникають.

**Клієнтський сценарій** (`scenario.py`): створити заняття на 3 місця → записати чотирьох клієнтів (четверта потрапляє в лист очікування) → повторний запис відхиляється (409) → прочитати стан → скасувати заняття → запис на скасоване заняття відхиляється (409). Вивід: [`scenario-output.txt`](scenario-output.txt).

## 5. Перевірки

### Поведінка API (`tests/test_api.py`, 19 тестів через справжній сервер)

| Що вимагає завдання | Тести |
|---|---|
| Успішний сценарій | `test_full_scenario_create_book_read_cancel` |
| Некоректні дані | `test_invalid_class_data_is_rejected_with_reason` (7 випадків: немає поля, рядок замість числа, `true` замість числа, неправильна дата, зайве поле, кінець раніше початку, 41 місце), `test_malformed_json_is_rejected`, `test_empty_client_id_is_rejected` |
| Відсутній ресурс | `test_missing_class_returns_404` (для всіх трьох операцій із `class_id`) |
| Заборонений перехід стану | `test_cancelling_twice_is_forbidden_transition`, `test_booking_cancelled_class_is_conflict` |
| Додатково | порушення правила (409 `rule_violation`), неправильний метод (405), відповіді відповідають схемам з `openapi.yaml`, кожна операція документує успіх і помилки |

### Контрактні перевірки

Підхід за мотивами Pact, без брокера: власний файл очікувань і два окремі тести.

- **Файл очікувань** [`booking-client.expectations.json`](../../backend/contracts/booking-client.expectations.json): 7 взаємодій. Для кожної є стан провайдера, запит, який надсилає клієнт, і очікувана відповідь. У відповіді описано **лише ті поля, які клієнт справді читає**, з правилами `equals` (точне значення) або `type` (тип).
- **Тест клієнта** (`tests/test_contract_consumer.py`): справжній провайдер не запускається. Тестова заглушка повертає **лише** поля з очікувань. Тест перевіряє, що клієнт надсилає саме записаний запит і правильно розбирає відповідь. Якби клієнт почав читати поле, якого немає в очікуваннях, тест упав би.
- **Перевірка провайдера** (`tests/test_contract_provider.py`): ті самі 7 взаємодій відтворюються на справжньому сервері. Перед кожною готується стан провайдера (наприклад, «заповнене заняття на 3 місця»), а відповідь порівнюється з правилами з файлу очікувань.

## 6. Експеримент: несумісна зміна

| Крок | Зміна в провайдері | Тест клієнта | Перевірка провайдера | Вивід |
|---|---|---|---|---|
| 1. Несумісна зміна | у `class_to_json` поле `free_places` перейменовано на `available_places` (тобто потрібне клієнту поле зникло) | 7 passed | **3 failed**: `create-class`, `get-class`, `cancel-class` з причиною «немає поля «free_places»» | [`contract-1-broken.txt`](contract-1-broken.txt) |
| 2. Сумісність відновлено | повернуто `free_places` | 7 passed | 7 passed | [`contract-2-fixed.txt`](contract-2-fixed.txt) |
| 3. Сумісна зміна | додано нове необов'язкове поле `room` | 7 passed | 7 passed | [`contract-3-optional-field.txt`](contract-3-optional-field.txt) |

**Що показав експеримент.** Несумісність виявила **перевірка провайдера**, тобто зміна зламана на боці провайдера. Тест клієнта при цьому пройшов, бо клієнт не змінювався й досі виконує свої очікування. Саме тому потрібні обидва тести: тест клієнта фіксує, що клієнту потрібно, а перевірка провайдера показує, чи провайдер це досі дає.

**Чому додавання необов'язкового поля сумісне.** Клієнт читає лише свої поля й ігнорує решту, а правила в очікуваннях не забороняють зайвих полів. Нове поле `room` старому клієнту просто не цікаве. Це видно на кроці 3.

**Чому зміна значення чи семантики несумісна, навіть якщо схема та сама.** Якщо, наприклад, `free_places` почне означати «кількість записаних», а не «вільних місць», тип лишиться `integer`, і перевірка схеми OpenAPI пройде. Але клієнт покаже людям неправду. Те саме зі зміною значень `status` (`scheduled` → `planned`): навіть якщо `enum` в OpenAPI оновити разом із кодом, схема буде валідною, а клієнт, що порівнює статус із `scheduled`, зламається. Такі зміни ловлять правила `equals` в очікуваннях клієнта, а не схема.

### Як повторити експеримент

1. У `backend/src/fitshed/api/http_api.py` у функції `class_to_json` замініть рядок `"free_places": gc.free_places,` на `"available_places": gc.free_places,`.
2. З папки `backend` виконайте `python -m pytest tests/test_contract_consumer.py tests/test_contract_provider.py` і переконайтеся, що впали 3 перевірки провайдера.
3. Поверніть рядок і запустіть ще раз: усі 14 проходять.

## 8. Обмеження

- Сховище в пам'яті: після перезапуску сервера заняття зникають.
- Сервер однопотоковий, тому навантаження й одночасний запис (СЯ-1, СЯ-3) тут не перевіряються.
- Автентифікації й контролю доступу немає: будь-хто може скасувати заняття. Це тема наступних робіт модуля 2.
- Перевірку відповідності OpenAPI зроблено через `jsonschema` для схем відповідей, а не повним валідатором специфікації.
- Контрактні перевірки працюють з власним файлом очікувань без Pact і брокера, як дозволяє завдання.

## 9. Висновок

Для FitShed спроєктовано REST API ресурсу «групове заняття» з чотирма операціями: створення, читання, запис клієнта та скасування заняття. Контракт описано в OpenAPI 3.1.1 з обмеженнями, прикладами та помилками 400, 404 і 409. Для кожної операції обґрунтовано метод і код відповіді, а різницю між 201 і 202 показано на прикладі сповіщень і майбутньої Saga.

API реалізовано як транспортний адаптер доменного ядра з ЛР 2: адаптер перевіряє лише структуру запиту, а всі бізнес-правила залишилися в агрегаті `GroupClass`. Клієнт виконує завершений сценарій через API. Автоматичні тести перевіряють успішний сценарій, некоректні дані, відсутній ресурс і заборонений перехід.

Контрактна перевірка складається з тесту клієнта на тестовій відповіді та перевірки справжнього провайдера за тим самим файлом очікувань. Перейменування поля `free_places` виявила саме перевірка провайдера (3 провали), а після відновлення всі перевірки пройшли. Додавання необов'язкового поля сумісність не порушило. Вибір REST зафіксовано в ADR-004.
